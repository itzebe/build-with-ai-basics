Finite — code map

Where everything lives in the finished app, and the route to follow to understand it. Three files, no dependencies, nothing hidden.

The whole app

index.html
The shell. Header, the empty #stack container the script fills, and the add form. No ritual content is hard-coded.
styles.css
Palette tokens, typography, the square sizes, and the card states. The squares are the only thing that moves.
app.js
All the logic, in five labelled sections: state, calculation, rendering, persistence, and adding a ritual.

That is the entire application. There is no build step and no dependency to install, so what you read is what runs.

The guided route

Follow these in order. Each stop is small and each one builds on the last.

app.js → remainingFrom(input) start here
The one piece of real logic. Converts both sides to days and divides, with Math.floor so the count never promises an instance that does not fit. Try changing weekly to daily and see the count jump.
app.js → buildCard(ritual)
Turns one ritual into DOM. Note the loop that creates one square per remaining instance — the grid is the count, not a picture of it.
app.js → spend(id, square)
The kernel. Adds .is-leaving, waits 150ms, then increments spent and re-renders. The whole product is this function.
app.js → save() and load()
load() validates every record with isUsableRitual() and throws away anything malformed, so bad data can never reach the screen as NaN.
styles.css → .sq and the size classes
Where the grid stays legible from 1 square to 2000, and where prefers-reduced-motion switches the animation off.

The state

One array, one storage key. Each ritual looks like this:

FieldMeaning
nameWhat the user called it.
freqdaily / weekly / monthly / yearly.
durationValueThe number they typed.
durationUnitdays / weeks / months / years.
totalWorked out once when created, then never recomputed.
spentHow many have been used. Just a number.

There is no remaining field. It is always total - spent, worked out when it is needed, so the stored number and the drawn grid cannot drift apart.

Everything is kept in localStorage["finite.rituals.v1"]. The .v1 means a future change of shape can be spotted rather than crashing on old data.

Try changing something

A small change to make it yours. The seed ritual in seed() is Saturday pancakes, weekly, 12 years. Replace it with a ritual of your own — the real frequency and the real length — then reload the page and clear the stored data so it re-seeds.

Watch what happens to the grid when you change the frequency from weekly to daily while leaving the duration alone. Same phase, ten times as many squares. That difference is the entire argument for drawing the grid instead of printing the number.

Then open spend() and delete the 150ms timeout, so it re-renders immediately. The interaction still works, but it stops feeling like the square is leaving. Put it back.

One thing to know

The --spent colour is barely used. A spent square leaves the grid rather than staying on screen greyed out, because the grid getting smaller is the point. The first draft of the spec had it the other way round, and checklist.md records the correction.
