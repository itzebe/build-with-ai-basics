Finite — code map

Where everything lives in the finished app, and the route to follow to understand it. Three files, no dependencies, nothing hidden.

The whole app

index.html
The shell. Header, the empty #stack container the script fills, and the add form. No ritual content is hard-coded.
styles.css
Palette tokens, typography, the square sizes, and the card states. The squares are the only thing that moves.
app.js
All the logic, in six labelled sections: dates, calculation, rendering, interaction, persistence, and adding a ritual.

That is the entire application. There is no build step and no dependency to install, so what you read is what runs.

The guided route

Follow these in order. Each stop is small and each one builds on the last.

app.js → occurrences(ritual) start here
The heart of the app. Turns a start date and a frequency into the date of every occurrence, using calendar arithmetic rather than milliseconds. Pure, so it returns the same list every call — which is what makes an index a stable way to name a moment.
app.js → splitOccurrences(list, today)
The one line of thinking the whole product rests on: which of those dates have passed, and which have not. Nothing about this is stored, so the grid moves on its own and can never be out of date.
app.js → buildCard(ritual)
Turns one ritual into DOM. Note that the loop creates one square per occurrence, in date order — the grid is the timeline, not a picture of it.
app.js → toggleKept(id, index, square)
The one interaction. It refuses future squares, then adds or removes the index in kept. Recording is reversible because it is a note about the past, not the moment itself.
app.js → notePassage()
Runs once at startup. Counts how many occurrences fell between the day you last looked and today, so the card can say what slipped by. The count is transient — a difference between two dates rather than a fact about the ritual, and storing it would let it go stale. That is why the old spent counter had to go.
app.js → handleKeydown()
The grid is one tab stop, not 626. Only a single square per grid carries tabIndex = 0; arrows move within it and clamp to the squares that can actually be acted on, because a disabled button cannot take focus. Without this, reaching the add form by keyboard meant pressing Tab 365 times.
app.js → save() and load()
load() validates every record with isUsableRitual() and throws away anything malformed, so bad data can never reach the screen as NaN. It also drops any kept index that no longer names a real occurrence.
index.html → the legend
The four swatches are static markup, and each carries the same state class the real squares do — .key-swatch.is-passed beside .sq.is-passed. The stylesheet styles both with one rule, so the legend cannot disagree with the grid it explains.
styles.css → .sq and the three states
Upcoming, passed, kept. Passed is deliberately paler than upcoming, so the past recedes — the opposite of a progress bar. Also where the grid stays legible from 1 square to 2000.

The state

One array, one storage key. Each ritual looks like this:

FieldMeaning
nameWhat the user called it.
freqdaily / weekly / monthly / yearly.
durationValueThe number they typed.
durationUnitdays / weeks / months / years.
startISOWhen the phase began. The timeline runs from here.
totalWorked out once when created, then never recomputed.
keptIndices of the occurrences you recorded being there for.
lastSeenISOThe day you last opened the app. Used only to count what slipped by.

There is no remaining field, and no passed field either. Both are worked out from startISO and today's date when the card is drawn. Nothing about the present is stored, so the stored data and the drawn grid cannot drift apart — and the grid moves on its own.

Everything is kept in localStorage["finite.rituals.v1"]. The .v1 means a future change of shape can be spotted rather than crashing on old data.

Try changing something

A small change to make it yours. The seed ritual in seed() is Saturday pancakes, weekly, 12 years, starting seven years ago. Replace it with a ritual of your own — the real frequency and the real length — then clear the stored data so it re-seeds.

Watch what happens to the grid when you change the frequency from weekly to daily while leaving the duration alone. Same phase, ten times as many squares. That difference is the entire argument for drawing the grid instead of printing the number.

Then find splitOccurrences() and change <= to <. One more square becomes upcoming, because an occurrence on today now counts as still to come. Small change, and it decides whether today counts as gone. Put it back.

Finally, to see the return-visit line without waiting a week: open the app, then in your browser's storage set lastSeenISO to a date a few weeks back and reload. The card will tell you how many moments passed in between.

One thing to know

The first version of this app only moved when you tapped it. That made the headline number a report on your own tapping rather than a fact about your life, and it was wrong the moment you stopped opening the app. The fix was to put the occurrences on real dates and derive everything from the clock, which is why there is no remaining or passed field anywhere. checklist.md records the change.
